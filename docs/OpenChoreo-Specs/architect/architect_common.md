Import rules, as practised:

- I: api/v1alpha1 is the only package every other layer may import — basis: it holds the CRD types and is imported by controllers, services, CLI and agents alike, while importing none of them [D: api/v1alpha1/groupversion_info.go:1].
- I: internal/ is closed to external consumers and `pkg/` is the deliberate export surface — basis: Go enforces `internal/` visibility at the compiler level, and `pkg/mcp` is the package `cmd/openchoreo-api` and `cmd/observer` both import [D: cmd/openchoreo-api/main.go:49].
- I: controllers do not render — the rendering pipeline lives in `internal/pipeline/*` and is called by the binding controllers rather than implemented in them — basis: `internal/pipeline/component/pipeline.go:5-11` documents the pipeline as the combiner of ComponentType, Traits, Workload and ReleaseBinding, and `internal/controller/releasebinding/` calls into it [D: internal/pipeline/component/pipeline.go:5].

OPEN: is the `internal/` vs `pkg/` split enforced anywhere, or maintained by convention? No import-linter configuration is present.

## Naming conventions

- **Controllers**: one package per kind at `internal/controller/<kind>/`, with the reconciler type named plainly `Reconciler` rather than `<Kind>Reconciler` [D: docs/contributors/adding-new-crd.md:60-72]. 34 such packages exist [D: internal/controller/component/controller.go:3].
- **CRD kinds**: platform-scoped kinds come in paired namespaced and cluster-scoped variants prefixed `Cluster` — `ComponentType`/`ClusterComponentType`, `Trait`/`ClusterTrait`, `ResourceType`/`ClusterResourceType`, `ProjectType`/`ClusterProjectType`, `Workflow`/`ClusterWorkflow`, `AuthzRole`/`ClusterAuthzRole` and the three plane kinds [D: api/v1alpha1/clustercomponenttype_types.go:141].
- **Type files**: `api/v1alpha1/<lowercasekind>_types.go` [D: api/v1alpha1/dataplane_types.go:172].
- **Generated files** are suffixed `.gen.go` or prefixed `zz_generated.` [D: internal/openchoreo-api/api/gen/server.gen.go:1], [D: api/v1alpha1/zz_generated.deepcopy.go:1].
- **Endpoints**: namespaced resources are `/api/v1/namespaces/{namespaceName}/<plural>`; cluster-scoped are `/api/v1/cluster<plural>`; sub-resources append a segment (`/schema`, `/status`, `/logs`, `/events`) [D: openapi/openchoreo-api.yaml:191-6210]. Three operations break the noun pattern and use a colon verb: `remote-connect:resolve`, `:authorize`, `:heartbeat` [D: internal/remoteconnect/authorize.go:68].
- **API versioning is not uniform**: most paths are `/api/v1`, but `autobuild`, `gitsecrets`, `secrets` and the release-binding `trigger` sit under `/api/v1alpha1` [D: openapi/openchoreo-api.yaml:3708], [D: openapi/openchoreo-api.yaml:6060].

OPEN: is `v1alpha1` on those four paths a stability signal, or an artefact of when each endpoint was added?
- **Commits**: Conventional Commits, validated in CI against the PR title [D: docs/contributors/github_workflow.md:137], [D: .github/workflows/lint-pr.yml:1].
- **Branches/merge**: squash-merge is the only strategy; the PR title becomes the commit message on `main` [D: docs/contributors/github_workflow.md:244-252].

## Design patterns

Sanctioned, each observable in the tree:

- **Spec-first HTTP.** `openapi/*.yaml` is the source of truth; models, server interface and client are generated from it into `internal/<service>/api/gen/` [D: make/golang.mk:184-206]. The server is mounted as a catch-all at `/` [D: cmd/openchoreo-api/main.go:377], so the route table is the spec, not the Go code.
- **Layered service call path.** Generated strict handler → `internal/openchoreo-api/api/handlers/` → `internal/openchoreo-api/services/<domain>/` → Kubernetes client [D: cmd/openchoreo-api/main.go:189-195].
- **Generated-then-hand-edited pairs.** The audit operation table is generated from each service's OpenAPI spec, while its exemptions are maintained by hand beside it [D: internal/openchoreo-api/audit/definitions.gen.go:1], [D: internal/openchoreo-api/audit/exemptions.go:1], [D: make/golang.mk:213-220].
- **Immutable release snapshots.** `ComponentRelease` freezes ComponentType, Traits and Workload; `ReleaseBinding` binds that snapshot to an Environment [D: docs/crds/renderedrelease.md:44-48].
- **RBAC from markers.** Controller permissions are declared as `+kubebuilder:rbac` comments on the reconciler and generated into `config/rbac/` [D: internal/controller/component/controller.go:6-19].

Rejected / absent:

- I: no ORM and no relational store in the control plane — basis: the survey found no DDL, migration or ORM model anywhere, and every persisted object is a CRD reconciled through the Kubernetes API [D: api/v1alpha1/groupversion_info.go:1]. State lives in etcd via the API server.

OPEN: the anti-patterns this team actively rejects are not written down anywhere in the repository. The `.golangci.yml` disable-list is the closest proxy, and it records tolerated noise, not rejected design.

## Code quality

- **Linting**: `golangci-lint` v2 with `default: none` and 29 explicitly enabled linters, including `gosec`, `gocyclo`, `errorlint`, `dupl`, `prealloc`, `lll` and `revive` [D: .golangci.yml:7-30]. Enabling by allowlist rather than disabling by denylist means a new upstream linter never lands silently.
- **`govet` runs with `enable-all`**, minus `fieldalignment` and `shadow` [D: .golangci.yml:70-75].
- **Full gate**: `make lint` = golangci-lint + license headers + trailing newlines [D: make/lint.mk:78].
- **License header** on every Go file, enforced by an in-repo tool [D: make/lint.mk:20], [D: make/lint.mk:24].
- **Generated code must be current**: `make code.gen-check` regenerates everything and fails on a dirty tree [D: make/lint.mk:164]. It covers CRD manifests, deepcopy, OpenAPI, helm charts, samples, mocks and audit tables [D: make/lint.mk:161].
- **Tests**: `make test` = Go + Python [D: make/lint.mk:166]; Go tests exclude `/e2e` and run under envtest assets [D: make/golang.mk:173].

OPEN: no coverage threshold is configured anywhere, though Codecov is wired into the README badge. Is there a target, and is it enforced?

OPEN: no file-size or function-length limit is configured; `gocyclo` is enabled but its threshold is not set in `.golangci.yml`.

## Security baseline

- **Static analysis**: `gosec` is enabled, with `G101`/`G117` (hardcoded-credential heuristics) and the `G7xx` taint-analysis family excluded as false-positive-prone; the exclusion for G703/G704/G705 cites the upstream issue [D: .golangci.yml:34-41].
- **Supply chain**: CodeQL, Trivy image scanning, periodic Trivy and OpenSSF Scorecard all run as workflows [D: .github/workflows/codeql.yml:1], [D: .github/workflows/trivy-image-scan.yaml:1], [D: .github/workflows/periodic-trivy.yaml:1], [D: .github/workflows/scorecard.yml:1].
- **Provenance**: every commit must carry a DCO `Signed-off-by` line [D: docs/contributors/github_workflow.md:190-204].
- **Authorization** is centralised in a Casbin PDP rather than per-handler checks; entitlements are serialised once per request [D: internal/authz/casbin/pdp.go:251].
- **Audit** is middleware-driven and its operation table is generated from the API spec, so a new endpoint cannot silently escape auditing — it must be regenerated or explicitly exempted [D: make/golang.mk:213-220], [D: internal/openchoreo-api/audit/exemptions.go:1].
- **Token egress is allowlisted** in the compatibility scanner: "Hostnames permitted to receive an Authorization token. Kept as an explicit allowlist so a misconfigured or redirected URL cannot exfiltrate a secret (e.g. GITHUB_TOKEN) to an arbitrary host." [D: .github/scripts/external_compatibility_scan.py:44]
- **Auth ordering on the two data-plane routes.** The exec and wirelogs handlers are registered outside `jwtMiddleware`, on a separate top-level mux [D: cmd/openchoreo-api/main.go:338], [D: cmd/openchoreo-api/main.go:368-371]. The comment at that site records the intent in the authors' own words: "auth short-circuits a rejected request and never calls next… These two routes reach the data plane — a live shell and a live traffic stream".
- **Secrets in config** are read by key from env/file via koanf; the survey flagged 9 secret-shaped keys, and no value for any of them appears in this hub [D: internal/occ/cmd/login/login.go:37].

OPEN: there is no `.env.example` in the repository, so the required-vs-optional split for configuration is inferred from code reads only. Which keys are mandatory in a production install?

OPEN: log redaction exists for Hubble flow data [D: internal/cluster-agent/hubble_redact.go:1] — is there a general redaction policy for the API and observer logs, or only that one path?

## Review checklist

Derived from what CI actually blocks on, plus the two rules the contributor docs state. A reviewer or agent should be able to answer yes to all of these before approving:

- [ ] `make lint` passes — golangci-lint, license headers, trailing newlines [D: make/lint.mk:78]
- [ ] `make code.gen-check` leaves the tree clean; no generated file was hand-edited [D: make/lint.mk:164]
- [ ] `make test` passes (Go + Python) [D: make/lint.mk:166]
- [ ] PR title is a Conventional Commit — it becomes the squashed commit message [D: docs/contributors/github_workflow.md:137], [D: docs/contributors/github_workflow.md:249]
- [ ] Every commit carries `Signed-off-by` (DCO) [D: docs/contributors/github_workflow.md:190]
- [ ] The AI-assistance box in the PR template is ticked if AI generated any content [D: docs/contributors/AI-POLICY.md:24-27]
- [ ] New CRD fields are reflected in `config/crd/bases/` via `make manifests`, and new controller permissions via `+kubebuilder:rbac` markers [D: internal/controller/component/controller.go:6]
- [ ] A new API operation is present in `openapi/*.yaml` first, and `make audit-gen` has been re-run [D: make/golang.mk:213]

OPEN: the items above are what CI enforces. What does this team check in review that CI does not — architectural fit, naming judgement, test quality? None of it is written down, and that unwritten list is the real checklist.
